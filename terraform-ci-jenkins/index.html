Scan the code. Policy the plan. Approve before apply.

A Terraform CI/CD pipeline for platform teams — built for envs/dev/lambda on Jenkins EC2 Fleet. Secrets and lint run in parallel, the plan becomes a JSON artifact, Conftest/OPA judges the change, Infracost prices it, then a human gate unlocks terraform apply.

checkout secrets lint plan policy approve apply

The durable artifact is tfplan.binary (+ JSON for policy/cost). Apply never re-plans — it executes the approved plan file.

Policy-as-Code · what Conftest denies

Remote state · S3 + DynamoDB locking

Interview gold: state is the source of truth for “what exists.” Two engineers (or two Jenkins jobs) must never write it at once — that’s what the DynamoDB lock is for.

backend.hcl (lambda stack)

Partial config passed at init: terraform init -backend-config=backend.hcl

bucket = "terraform-backend-venkata"
key = "dev/lambda/terraform.tfstate"
region = "ap-south-1"
encrypt = true
kms_key_id = "alias/terraform-backend"
dynamodb_table = "terraform-backend-venkata-locks"

Why not local state?

Local terraform.tfstate on a laptop breaks team CI — lost locks, no shared inventory, secrets on disk.

S3 shared, durable state object
Versioning recover bad applies / accidents
KMS encrypt state at rest
DynamoDB mutual exclusion (LockID)
Per-key one state file per stack path

What happens when plan/apply starts:

1 Acquire lock Put item in DynamoDB with LockID = state path
2 Read state GET object from S3 bucket/key
3 Plan / Apply Compute / mutate cloud resources
4 Write state PUT new state JSON to S3 (versioned)
5 Release lock Delete DynamoDB lock item
concurrent job Lock already held Second plan/apply fails fast: “Error acquiring the state lock” — no corrupted state
stale lock Crash mid-apply Lock may linger → inspect DynamoDB, confirm no run is active, then terraform force-unlock <LOCK_ID>

Interview answers — state & locking

Q · Why S3 for Terraform state?

State must be shared and durable across engineers and Jenkins agents. S3 gives a single object per stack (key = envs/…/terraform.tfstate), with versioning so a bad apply can be rolled back to a previous state object, and KMS encryption because state often contains resource IDs and sensitive attributes.

Q · What does DynamoDB locking actually prevent?

Two writers updating the same state file. Without a lock, two applies can both read “old” state, both write resources, then overwrite each other’s state → drift and ghost resources. DynamoDB stores a lock item keyed by LockID (the state path). Only one process holds it; others error until it’s released.

Q · Walk me through a locked apply

Jenkins runs terraform init -backend-config=backend.hcl → on plan/apply Terraform acquires the DynamoDB lock → reads state from S3 → executes → writes new state to S3 → releases the lock. Our pipeline also freezes a tfplan.binary so apply uses the same plan the human approved.

Q · What if the pipeline dies while locked?

The DynamoDB item can remain. First check CloudTrail/Jenkins that no apply is still running. Then terraform force-unlock <ID> (or delete the lock item). Never force-unlock while another apply is live — that’s how you corrupt state.

Q · S3 versioning vs DynamoDB — who does what?

S3 = store + history of the state file. DynamoDB = short-lived lease so only one writer exists. Versioning does not replace locking; locking does not replace backups. You need both for a team CI story.

Q · Modern nuance (Terraform ≥ 1.10)

AWS S3 backend can also use a native lock file in the bucket (use_lockfile = true) instead of — or alongside — DynamoDB. Interview-safe answer: “We used DynamoDB LockID for exclusive access; native S3 locking is the newer option, same problem different mechanism.”

Infrastructure changes are planned once, policy-checked, costed, and only then applied — by a human who saw the evidence.

$ terraform init -backend-config=backend.hcl # S3 + DynamoDB lock
$ terraform plan -out=tfplan.binary # acquires lock → reads state
$ terraform show -json tfplan.binary > tfplan.json
$ conftest test tfplan.json --policy policy/ # OPA
$ terraform apply tfplan.binary # after Approve · writes state · releases lock
