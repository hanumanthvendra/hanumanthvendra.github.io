Platform / Infrastructure · Jenkins · Terraform · OPA

Scan the code. Policy the plan. Approve before apply.

A Terraform CI/CD pipeline for platform teams — built for envs/dev/lambda on Jenkins EC2 Fleet. Secrets and lint run in parallel, the plan becomes a JSON artifact, Conftest/OPA judges the change, Infracost prices it, then a human gate unlocks terraform apply.

checkout secrets lint plan policy approve apply

The durable artifact is tfplan.binary (+ JSON for policy/cost). Apply never re-plans — it executes the approved plan file.

Policy-as-Code · what Conftest denies

Rules live next to the stack in policy/terraform.rego. They evaluate the plan JSON — so open CIDRs and missing encryption never reach apply quietly.

deny[] examples

deny SG ingress 0.0.0.0/0 except 80/443
deny S3 without SSE
deny EBS / RDS without encryption
deny public S3 ACLs
deny missing tags: Owner, CostCenter, Environment
deny ALB listener TLS < 1.2

Why this fits a platform team

Same pipeline shape for every env stack under envs/ — network, eks, lambda — with a human gate before cloud mutation.

Shift-left secrets + lint before plan
Plan-once binary is the apply input
Policy OPA on the change set
Cost Infracost before Yes
Evidence SARIF · JUnit · SBOM · graph

Who does what

Jenkins does

  • Clone, scan, fmt, lint, validate, plan
  • Run Conftest + Infracost on the plan
  • Wait for Approve → terraform apply tfplan.binary
  • Archive artifacts; Slack on failure

Pipeline never

  • Apply without the Yes gate
  • Re-run plan after approval (uses saved binary)
  • Skip remote state / backend.hcl init
  • Hide secrets findings (marks UNSTABLE)

Infrastructure changes are planned once, policy-checked, costed, and only then applied — by a human who saw the evidence.

$ terraform plan -out=tfplan.binary
$ terraform show -json tfplan.binary > tfplan.json
$ conftest test tfplan.json --policy policy/ # OPA
$ terraform apply tfplan.binary # after Approve
