EKS Auto Mode · Istio sidecar · istio-cni

Request hits the gateway, then the sidecar — not the app first.

From the Medium guide: install Istio on EKS Auto Mode with istio-cni (no privileged init), label the namespace for injection, restart pods to 2/2, then traffic enters via istio-ingressgateway and hops Envoy → app. East-west rides mTLS between sidecars. istiod is the brain that programs every proxy.

Why istio-cni on EKS

Classic init containers need NET_ADMIN — clashes with Pod Security. CNI does redirect on the node instead.

Interview Q&A

Short answers you can say out loud — aligned with the Medium guide.

Q · Walk me through a request into the mesh

Client hits the AWS load balancer → istio-ingressgateway (Envoy) matches a Gateway / VirtualService → Kubernetes Service → destination Pod. Inside the pod, traffic hits the istio-proxy sidecar first, then the app container on localhost. The app never sees the public network.

Q · What does istiod do?

Control plane. It discovers services, issues certificates for identities, and pushes config to every Envoy (ingress + sidecars) over xDS. Data plane carries packets; istiod does not.

Q · Why enable Istio CNI on EKS Auto Mode?

Sidecar injection used to rely on an init container with NET_ADMIN, which Pod Security / restricted policies often block. istio-cni configures traffic redirection at the node/CNI layer so pods inject cleanly without that privilege escalation.

Q · I labeled the namespace — pods still 1/1. Why?

Injection happens at pod create time. Existing pods must be restarted/redeployed so the mutating webhook adds the sidecar. Then expect 2/2 Ready.

Q · How does east–west traffic stay secure?

Sidecar A opens an mTLS connection to sidecar B using mesh identities (SPIFFE-style). Apps still speak plain HTTP to their local proxy; encryption and auth are the sidecars’ job.

Q · Gateway vs VirtualService?

Gateway = which ports/hosts the ingress Envoy listens on (the edge). VirtualService = routing rules (path, weight, retries, timeouts) that send that traffic to a destination service/version.

Q · How do you verify the mesh is healthy?

kubectl -n istio-system get pods → istiod, ingressgateway, cni up. App pods 2/2. istioctl proxy-status → proxies SYNCED to istiod. Optional: Kiali / Prometheus addons for traffic graphs.

Q · Metrics / HPA on Auto Mode?

EKS Auto Mode already ships a compatible metrics-server — don’t fight it with a generic install. Confirm kubectl top nodes/pods and HPA shows real CPU, not <unknown>. Sidecars cost ~100m/256Mi each — size accordingly.

On EKS Auto Mode, Istio’s job is clear: ingress Envoy at the edge, sidecar Envoy beside every pod, istiod programming both — with istio-cni keeping injection EKS-safe.

$ istioctl install --set components.cni.enabled=true # + ingressgateway
$ kubectl label namespace demo istio-injection=enabled
$ kubectl rollout restart deploy -n demo # pods become 2/2
$ istioctl proxy-status # SYNCED
