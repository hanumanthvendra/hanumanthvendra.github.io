Jenkins · Helm · Argo CD · Argo Rollouts

Pin once in Git. Promote the same digest through stages.

Jenkins runs eight explicit stages — scan, build, scan again, then a human Approve before pinning. Argo CD renders one Helm chart with env + cluster overlays. Argo Rollouts blue/green promotes — auto in dev, pause in stage and prod. Jenkins never kubectl applys.

CI stage human gate Git pin Argo sync auto-promote

The artifact that moves is an immutable image digest written into Git — not a Jenkins deploy step. Clusters converge to whatever Git says.

values.yaml — the shared pin

Jenkins stage 08 rewrites only backend.image.tag and backend.image.digest. Everything else in the chart defaults stays put. Every Argo Application starts from this file.

What gets written

One commit. One pin. All environments read it — capacity and promote behaviour come from overlays, not a second image.

backend:
image:
registry: "172.18.0.20:5000"
repository: zerotrust-backend
tag: "04d6d5d" # ← Jenkins
digest: "sha256:e9da…" # ← Jenkins
services.active → zerotrust-backend-active
services.preview → zerotrust-backend-preview
blueGreen.* → defaults (overlays override)

Base pin + env overlays (promote/capacity) + cluster overlays (identity).

ApplicationSet — how clusters get an Application

gitops/applicationset.yaml uses a list generator. Each element becomes one Argo Application named zerotrust-{{cluster}}, pointing at the same chart path with different overlays.

List generator → apps

Add a prod row only after the cluster Secret is registered in Argo CD.

generators.list.elements:
- env: dev cluster: eks-sim
url: https://kubernetes.default.svc
→ App zerotrust-eks-sim
- env: stage cluster: aks-sim
url: <registered Secret>
→ App zerotrust-aks-sim
# - env: prod cluster: gke-prod (commented)

Helm merge per Application

Chart default first; env then cluster overlays. Later keys win.

source.path: charts/zerotrust-apps
destination.namespace: apps
① values.yaml # chart default pin
② values-{{env}}.yaml # valueFiles[0]
③ values-{{cluster}}.yaml # valueFiles[1]
syncPolicy: automated prune + selfHeal
ignoreDifferences: Rollouts Service selector

Promotion path

Blue/green with a Preview Service for smoke. Frontend always calls zerotrust-backend-active — never a ReplicaSet or preview Service.

02 · staging

aks-sim

same digest

human promote

Who does what

The hard rule that keeps GitOps honest: CI produces evidence and writes desired state. CD reconciles live state.

Jenkins does (01→08)

  • 01–04: Checkout → Gitleaks → SAST → Helm validate
  • 05–06: Kaniko build :<git-sha> → Trivy (CRITICAL fails)
  • 07: Human Approve GitOps input gate
  • 08: Commit tag + digest to values.yaml

Jenkins never

  • kubectl apply / helm upgrade
  • Patch Active / Preview Services
  • Call rollouts promote (preferred model)
  • Rebuild on its own chore(gitops): commits

Desired state lives in Git. Clusters converge through Argo CD. Traffic flips through Rollouts. Promote is a deliberate act on an already-scanned digest — not a rebuild.

$ make gitops # Jenkins + Argo CD + Rollouts + ApplicationSet
$ kubectl argo rollouts promote backend -n apps --context kind-aks-sim
